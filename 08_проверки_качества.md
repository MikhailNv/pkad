# Этап 8. Проверки качества данных и контроль результатов загрузки

**Команда 06 · «Доставка посылок»**

> Этап 8. Добавить проверки качества данных и контроль результатов загрузки.

Код: `sql/08_quality_control.sql`. Шаг pipeline — `core.step_07_quality_checks(run_id)`, вызывается оркестратором последним.

## 1. Объекты контроля

| Объект | Что хранит |
| :--- | :--- |
| `core.etl_run_log` | журнал запусков: время, статус (`SUCCESS` / `CHECKS_FAILED`), баланс RAW, число непройденных проверок, отпечаток RAW на старте |
| `core.run_step_log` | результат и время каждого шага запуска |
| `core.dq_check_result` | результат каждой проверки в каждом запуске |
| `core.run_metric` | контрольные показатели запуска: количества строк, суммы, md5 таблиц |
| `core.v_run_history` | история запусков с признаком `balance_ok` |
| `core.v_run_comparison` | сравнение двух последних запусков по всем показателям |
| `core.v_dq_last_run` | проверки последнего запуска |
| `core.v_raw_processing_stats` | исходных = загружено + карантин + дубли + неучтённые (по `raw_row_id`) |
| `core.v_raw_outcome_breakdown` | итог строк RAW в разрезе причин |

Журнал не очищается между запусками — по нему видна история.

```sql
SELECT * FROM core.v_run_history;
SELECT * FROM core.v_dq_last_run;
SELECT * FROM core.v_run_comparison;
SELECT * FROM core.v_raw_processing_stats;
SELECT * FROM core.v_raw_outcome_breakdown;
```

## 2. Проверки качества

25 проверок: 22 уровня **ERROR** (должны давать 0, иначе запуск получает статус `CHECKS_FAILED`)

Проверки 1–10 перенесены из `sql/05_checks.sql` и теперь сохраняются по каждому запуску; 11–22 добавлены для core и витрин.

**Проверка, что проверки работают.** В транзакции удалили одно событие из core и вызвали шаг 07:
сработали `LOAD_ROW_NOT_IN_CORE`, `CORE_COUNTS_MISMATCH`, `MART_SHIPMENT_RECONCILE`, `MART_EVENT_DAILY_RECONCILE`
(4 ошибки, затем `ROLLBACK`).

## 3. Статистика обработки RAW

Считается по идентификаторам строк RAW (`raw_row_id`), а не по строкам core. Категории не пересекаются:
у каждой строки ровно один итог (`core.raw_row_outcome`, PK `raw_row_id`), приоритет DUPLICATE → QUARANTINE → LOAD.

| Исходных | Загружено | Карантин | Дубликаты | Неучтённые | Баланс |
| ---: | ---: | ---: | ---: | ---: | :---: |
| 10 178 | 8 727 | 1 273 | 178 | 0 | 10 178 = 8 727 + 1 273 + 178 + 0 ✔ |

Карантин по основной причине (`core.v_raw_outcome_breakdown`):

| Причина | Строк | % RAW |
| :--- | ---: | ---: |
| `DT_PLACEHOLDER` — заглушка вместо даты | 352 | 3.46 |
| `DT_EMPTY` — дата не заполнена | 297 | 2.92 |
| `STATUS_PLACEHOLDER` — `???` вместо статуса | 171 | 1.68 |
| `DT_INVALID_TIME` — несуществующее время | 136 | 1.34 |
| `DT_INVALID_DATE` — несуществующая дата | 134 | 1.32 |
| `DT_RELATIVE` — «сегодня утром» и т.п. | 130 | 1.28 |
| `STATUS_MISLABELED` — «Доставлено» вместо базового этапа | 53 | 0.52 |
| **Итого карантин** | **1 273** | 12.51 |

Каждая строка RAW даёт не больше одного события, поэтому событий в core столько же, сколько строк LOAD: 8 727.
