`deploy.sql` можно запускать повторно: таблицы core не пересоздаются, журнал запусков и ручная
обработка карантина сохраняются. RAW скрипты только читают.

Первым выполняется `sql/00_check_core.sql`: если в core остались таблицы другой структуры (например, от учебного
DDL этапа 3 для ER-схемы), развёртывание останавливается с подсказкой. Тогда выполните `sql/00_reset_core.sql`
(удаляет объекты core, кроме `report_profile_*`; RAW не трогает) и повторите `deploy.sql`.

### Обновление и пересоздание

Функция читает RAW при каждом вызове — после появления новых строк достаточно
просто вызвать её снова, ничего пересоздавать не нужно.

Исходный код функции хранится в самой БД (принцип «всё решение хранится в БД»):

```sql
SELECT pg_get_functiondef('core.report_profile_raw'::regproc);
```

Пересоздание — обычный `CREATE OR REPLACE FUNCTION` с тем же телом. ⚠️ Это **DDL**,
поэтому запускать без `PGOPTIONS=…default_transaction_read_only=on`, иначе получите
`cannot execute ... in a read-only transaction`. Если меняется состав `RETURNS TABLE`,
перед пересозданием нужен `DROP FUNCTION`.

### Место в архитектуре

Функции **не входят** в pipeline `step_01…07`: это инструмент обследования, а не шаг
загрузки. Вызываются вручную — до загрузки и повторно после появления новых строк в RAW,
чтобы увидеть, как изменился профиль. Контрольный баланс
`RAW = загружено + карантин + дубликаты + неучтённые` проверяется в `step_07_quality_checks`.
