# Практическая работа № 2. Управление НСИ

## Что это за работа

Реализован учебный механизм изменения справочных данных через заявки и их согласование.
Все новые объекты создаются в отдельной схеме `nsi`, исходные данные и существующий ETL не изменяются.

Вариант: **06, «Доставка посылок»**. В качестве справочника взяты статусы событий доставки:
`Создано`, `Принято`, `Сортировочный центр`, `В пути`, `Передано курьеру`, `Доставлено`.

Работа выполнена в простом «студенческом» стиле: без триггеров, очередей, ролей и сложной архитектуры.
Основная логика собрана в двух процедурах на PL/pgSQL, физическое удаление запрещено двумя правилами (`RULE`).

## Как запустить

Скрипты рассчитаны на запуск через `psql`.

```bash
psql -h <host> -p <port> -U <user> -d <database> -v ON_ERROR_STOP=1 -f 01_nsi.sql
psql -h <host> -p <port> -U <user> -d <database> -v ON_ERROR_STOP=1 -f 02_create_requests.sql
```

## Модель данных

### Справочник `nsi.shipment_status`

| Поле | Тип | Обязательное | Назначение |
| :--- | :--- | :---: | :--- |
| `status_id` | `integer` | да | Первичный ключ, генерируется автоматически |
| `code` | `varchar(20)` | да | Код статуса, уникальный |
| `name` | `varchar(100)` | да | Наименование статуса |
| `is_active` | `boolean` | да | Признак активности записи |
| `valid_from` | `date` | да | Дата начала действия записи |
| `valid_to` | `date` | нет | Дата окончания действия записи |
| `created_at` | `timestamp` | да | Когда запись создана |
| `updated_at` | `timestamp` | да | Когда запись последний раз изменена |

Ограничения:

- `code` уникален, поэтому одинаковых кодов быть не может;
- `valid_to` либо пустой, либо больше или равен `valid_from`;
- физическое удаление строк запрещено правилом `rl_shipment_status_no_delete`. Вывод из использования делается через `is_active = false` и заполнение `valid_to`.

Первоначально в справочник загружаются шесть статусов:

| Код | Наименование |
| :--- | :--- |
| `CREATED` | Создано |
| `ACCEPTED` | Принято |
| `SORTING` | Сортировочный центр |
| `IN_TRANSIT` | В пути |
| `HANDED_TO_COURIER` | Передано курьеру |
| `DELIVERED` | Доставлено |

Дата начала действия у всех записей — `2026-01-01`, дата окончания пустая, признак активности — `true`.
Повторный запуск `01_nsi.sql` не создаёт дубли: используется `ON CONFLICT (code) DO NOTHING`.

### Заявки `nsi.change_request`

| Поле | Тип | Назначение |
| :--- | :--- | :--- |
| `request_id` | `bigint` | Первичный ключ заявки |
| `status_id` | `integer` | Ссылка на изменяемую запись справочника. Для INSERT заполняется после применения |
| `operation_type` | `varchar(10)` | Тип операции: `INSERT`, `UPDATE` или `DELETE` |
| `new_code` | `varchar(20)` | Новый код (для INSERT обязателен, для UPDATE может быть пустым) |
| `new_name` | `varchar(100)` | Новое наименование |
| `request_status` | `varchar(10)` | Статус заявки: `NEW`, `APPROVED` или `REJECTED` |
| `author` | `varchar(100)` | Автор заявки |
| `created_at` | `timestamp` | Дата создания заявки |
| `reviewed_at` | `timestamp` | Дата рассмотрения заявки |
| `reviewer` | `varchar(100)` | Ответственный за рассмотрение |
| `comment` | `text` | Комментарий |
| `is_applied` | `boolean` | Признак того, что заявка уже применена |
| `applied_at` | `timestamp` | Когда заявка была применена |

Ограничения:

- `operation_type` может принимать только `INSERT`, `UPDATE`, `DELETE`;
- у `INSERT` должны быть заполнены `new_code` и `new_name`;
- у `UPDATE` должна быть ссылка на запись и хотя бы одно новое значение;
- у `DELETE` должна быть ссылка на запись;
- `request_status` может принимать только `NEW`, `APPROVED`, `REJECTED`;
- у новой заявки `reviewed_at` пустой, у рассмотренной — заполнен;
- применённой может быть только утверждённая заявка.

Для ускорения обработчика создан индекс по полям `(request_status, is_applied)`.

### Запрет физического удаления

На обе таблицы созданы правила:

```sql
CREATE OR REPLACE RULE rl_shipment_status_no_delete AS
    ON DELETE TO nsi.shipment_status
    DO INSTEAD NOTHING;

CREATE OR REPLACE RULE rl_change_request_no_delete AS
    ON DELETE TO nsi.change_request
    DO INSTEAD NOTHING;
```

Любой `DELETE` по этим таблицам вместо удаления ничего не делает (`DELETE 0`), поэтому строки справочника
и история заявок сохраняются. Правило — самый короткий способ запрета без написания триггерной функции.

## Жизненный цикл заявки

1. Автор создаёт заявку. Она получает статус `NEW`, `is_applied = false`, `reviewed_at = NULL`.
2. Ответственный рассматривает заявку:
   - `APPROVED` — заявка разрешена к применению, заполняются `reviewed_at` и `reviewer`;
   - `REJECTED` — заявка отклонена, также заполняются `reviewed_at` и `reviewer`.
3. Обработчик `nsi.apply_approved_requests()` берёт только заявки со статусом `APPROVED` и `is_applied = false`.
4. После успешного применения у заявки выставляется `is_applied = true` и `applied_at = now()`.
5. Отклонённые заявки и старые применённые заявки остаются в таблице навсегда. История не удаляется.

## Как работает `02_create_requests.sql`

Процедура `nsi.create_demo_requests(p_author varchar DEFAULT 'demo_user')` создаёт три заявки разных типов.

### 1. Добавление нового значения (INSERT)

Добавляется новый статус:

- код: `CITY_SORTING`;
- наименование: `Сортировка в городе`;
- автор: значение параметра `p_author`;
- комментарий: `Добавление нового статуса`.

Заявка создаётся только если такого кода ещё нет в справочнике и нет такой же заявки на добавление.

### 2. Изменение существующего значения (UPDATE)

Находится статус с кодом `ACCEPTED`. Для него предлагается новое наименование `Принято в обработку`.
Код не меняется: в реальной НСИ код обычно стабилен, потому что на него могут ссылаться другие системы.

Заявка создаётся только если текущее наименование ещё не равно новому и такой заявки ещё нет.

### 3. Вывод из использования (DELETE)

Находится статус с кодом `SORTING`. Заявка предлагает сделать его неактивным.
Физического удаления нет: при применении будет установлено `is_active = false` и заполнено `valid_to`.

Заявка создаётся только если статус ещё активен и по нему нет неприменённой заявки на удаление.

Все три заявки создаются в статусе `NEW`. Повторный вызов процедуры не создаёт одинаковые заявки.

## Как работает `03_apply_requests.sql`

Процедура `nsi.apply_approved_requests()` читает заявки в цикле:

- условие отбора: `request_status = 'APPROVED' AND is_applied = false`;
- сортировка: по `request_id`, то есть в порядке создания;
- строки блокируются через `FOR UPDATE`, чтобы два одновременных запуска не обработали одну и ту же заявку.

Дальше выполняется действие в зависимости от `operation_type`.

### INSERT

- Проверяется, нет ли уже записи с таким `new_code`.
- Если записи нет, она добавляется в `nsi.shipment_status`:
  - `is_active = true`;
  - `valid_from = CURRENT_DATE`;
  - `valid_to = NULL`.
- В заявку записывается полученный `status_id`, выставляются `is_applied = true` и `applied_at`.
- Если код уже существует, заявка всё равно помечается применённой, а в комментарий добавляется пояснение.
  Это защищает от повторных попыток и дублей.

### UPDATE

- Если в заявке указан `new_code` и такой код уже есть у другой записи, справочник не меняется.
  Заявка помечается применённой, а в комментарий добавляется `Не применена: код уже существует` — так же, как для INSERT.
  Без этой проверки нарушение уникальности прервало бы всю процедуру, и остальные утверждённые заявки
  тоже не применились бы.
- Иначе у выбранной записи обновляются только те поля, которые заполнены в заявке:
  - `new_code`, если он указан;
  - `new_name`, если он указан.
- Также обновляется `updated_at`.
- Заявка помечается применённой.

### DELETE

- У выбранной записи выставляется `is_active = false`.
- В `valid_to` записывается `GREATEST(CURRENT_DATE, valid_from)`, чтобы дата окончания не оказалась раньше даты начала.
- Заявка помечается применённой.
- Строка из таблицы не удаляется.

### Защита от повторного применения

Главная защита — флаг `is_applied`. Обработчик выбирает только строки, где `is_applied = false`.
После применения флаг становится `true`, поэтому повторный запуск процедуры не делает изменений ещё раз.
Дополнительно для INSERT и UPDATE проверяется уникальность кода, а для DELETE — что запись ещё активна.

## Что делает `04_demo.sql`

Скрипт показывает полный сценарий.

1. Показывает исходное состояние справочника.
2. Вызывает `nsi.create_demo_requests('student_ivanov')` и показывает три новые заявки.
3. Утверждает все три заявки от `student_ivanov`:
   - `request_status = 'APPROVED'`;
   - `reviewed_at = now()`;
   - `reviewer = 'manager_petrov'`.
4. Добавляет четвёртую заявку на изменение статуса `DELIVERED` и сразу переводит её в `REJECTED`.
   Это нужно, чтобы показать, что отклонённые заявки не применяются.
5. Вызывает `nsi.apply_approved_requests()`.
6. Показывает справочник и таблицу заявок после применения.
7. Ещё раз вызывает `nsi.apply_approved_requests()`.
8. Проверяет, что количество применённых заявок не изменилось, количество строк в справочнике не выросло,
   а одинаковых кодов нет.
9. Показывает отклонённую заявку и подтверждает, что она не применена.
10. Пытается физически удалить статус `SORTING` и отклонённую заявку и показывает,
    что количество строк в обеих таблицах не изменилось (7 и 4).

## Ожидаемый результат демонстрации

После выполнения `04_demo.sql`:

- в справочнике появляется новая запись `CITY_SORTING` с наименованием `Сортировка в городе`;
- у записи `ACCEPTED` наименование меняется с `Принято` на `Принято в обработку`;
- у записи `SORTING` выставляется `is_active = false`, а `valid_to` заполняется текущей датой;
- заявки INSERT, UPDATE и DELETE получают `is_applied = true`;
- отклонённая заявка по статусу `DELIVERED` остаётся со статусом `REJECTED` и `is_applied = false`;
- повторный запуск обработчика не добавляет новых строк и не меняет уже применённые заявки;
- попытка `DELETE` не удаляет ни строки справочника, ни заявки.

Итоговое количество строк в справочнике: `6 + 1 = 7`.
Итоговое количество заявок в демонстрации: `4`, из них применены `3`.

## Проверочные запросы

Посмотреть справочник:

```sql
SELECT status_id, code, name, is_active, valid_from, valid_to
FROM nsi.shipment_status
ORDER BY status_id;
```

Посмотреть заявки:

```sql
SELECT request_id, operation_type, status_id, new_code, new_name,
       request_status, author, reviewer, is_applied, applied_at, comment
FROM nsi.change_request
ORDER BY request_id;
```

Проверить, что нет дублей кодов:

```sql
SELECT code, count(*)
FROM nsi.shipment_status
GROUP BY code
HAVING count(*) > 1;
```

Проверить, что применены только утверждённые заявки:

```sql
SELECT *
FROM nsi.change_request
WHERE is_applied = true
  AND request_status <> 'APPROVED';
```

Запрос должен вернуть ноль строк.

Проверить, что физического удаления не было:

```sql
SELECT count(*) AS total_rows
FROM nsi.shipment_status;
```

Количество строк не уменьшается ни после заявок на удаление, ни после прямого `DELETE`.

## Повторный запуск

- `01_nsi.sql` можно запускать повторно: схема и таблицы создаются через `IF NOT EXISTS`,
  правила — через `CREATE OR REPLACE RULE`, начальные данные вставляются через `ON CONFLICT (code) DO NOTHING`.
- `02_create_requests.sql` и `03_apply_requests.sql` используют `CREATE OR REPLACE PROCEDURE`,
  поэтому их можно запускать повторно без ошибок.
- `04_demo.sql` можно запускать повторно. Он не создаст новые демонстрационные заявки,
  если изменения уже есть в справочнике, и не применит уже применённые заявки второй раз.

## Что сознательно не сделано

Это учебная работа, поэтому в ней нет:

- триггеров, которые запрещают менять справочник через `UPDATE`/`INSERT` в обход процедуры
  (запрещено только удаление);
- отдельной роли или пользователя для согласования;
- веб-интерфейса или формы заявки;
- автоматического заполнения `reviewed_at` через триггер;
- сложного журнала аудита: история хранится в самих заявках.

При этом все требования задания выполнены: объекты находятся в схеме `nsi`, изменения идут только по утверждённым заявкам,
удаление логическое, повторная обработка не создаёт дублей, история заявок сохраняется.
