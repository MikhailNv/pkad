## 3. Этап 5. Очистка

### 3.1 Принципы

1. **Функции не падают на мусоре.** Каждая возвращает значение и код ошибки `err`; `err IS NULL` — разобрано. Код ошибки становится причиной карантина.
2. **Лучше карантин, чем угадывание.** Принимаются только формы, которые разбираются однозначно.
3. **Справочники строятся из RAW.** Жёстко заданы только бизнес-словари: статусы, текстовые заглушки, названия месяцев, сокращения городов.

### 3.2 Функции

| Функция | Вход → выход | Коды ошибок |
| :--- | :--- | :--- |
| `fn_norm_text` | trim, невидимые символы, все виды пробелов → один; заглушки (`NULL`, `неизвестно`, `не указан`, `???` …) → NULL | — |
| `fn_parse_shipment_id` | `PKG-900001`, `№ PKG 900001`, `900001` → `PKG-900001` | `ID_EMPTY`, `ID_INVALID` |
| `fn_parse_ts` | дата и время в 7+ форматах → `timestamp` | `DT_EMPTY`, `DT_PLACEHOLDER`, `DT_RELATIVE`, `DT_UNKNOWN_FORMAT`, `DT_NO_TIME`, `DT_INVALID_DATE`, `DT_INVALID_TIME` |
| `fn_parse_status` | регистр, `ё`, пробелы, точка в конце → код статуса | `STATUS_EMPTY`, `STATUS_PLACEHOLDER`, `STATUS_UNKNOWN` |
| `fn_parse_city` | префикс «г.», регистр, сокращения (`СПб`) → город из справочника | `CITY_EMPTY`, `CITY_UNKNOWN` |
| `fn_parse_route` | `из A в B`, `A -> B`, `A → B`, `A - B`, `A/B` → пара городов | `ROUTE_EMPTY`, `ROUTE_FORMAT`, `ROUTE_CITY_UNKNOWN` |
| `fn_parse_person` | ФИО в любой из встречающихся форм → человек из справочника | `PERSON_EMPTY`, `PERSON_CODE_ONLY`, `PERSON_INVALID`, `PERSON_UNKNOWN`, `PERSON_AMBIGUOUS`, `PERSON_CODE_CONFLICT`, `PERSON_ROLE_MISMATCH` |

### 3.3 Дата и время

Поддерживаются:

* `DD.MM.YYYY`, `DD/MM/YYYY`, `DD-MM-YYYY`, двузначный год `DD.MM.YY` (→ 20YY);
* `YYYY-MM-DD`, `YYYY/MM/DD`, `YYYY.MM.DD`, разделитель даты и времени — пробел или `T`;
* `YYYYMMDD HHMI[SS]`;
* `DD Mon YYYY` — английские и русские названия месяцев, полные и сокращённые;
* время `HH:MI[:SS]`, `AM`/`PM` (`12 AM → 00`, `12 PM → 12`), предлог «в» перед временем.

Календарь проверяется без исключений: `31.02.2026`, `29.02.2026`, `15.03.2026 25:61`, год `0000` дают код ошибки, а не падение.

**Порядок день/месяц.** Для форматов с точкой и слешем принят DD/MM. Обоснование на данных: в RAW нет ни одной даты с «месяцем» больше 12 во втором поле, а неоднозначные даты подтверждаются шагом между событиями (см. 3.6). В `03_tests.sql` есть проверка-страховка: если такая дата появится, тест упадёт.

### 3.4 ФИО

Нормализация: удаляется код `S/R/C##` в любом обрамлении (`S3 `, `[S3]`, `(S3)`, `ВолковS3`), `,` и `_` → пробел, нижний регистр, `ё → е`, цифра `0` между кириллическими буквами → `о`, инициалы разлепляются (`А.Иванов`).

Принимаются только однозначные формы (все 10 форм, встречающихся в RAW):

| Форма | Пример |
| :--- | :--- |
| Фамилия Имя / Имя Фамилия | `Иванов Алексей`, `Алексей Иванов` |
| Фамилия Имя Отчество | `Волков Николай Николаевич` |
| Фамилия + инициалы | `Голубев Е.М.`, `Н.М. Зайцев`, `А.Лебедев` |
| Только фамилия | `Волков` |
| Имя + инициал фамилии | `Роман К.`, `Татьяна С.` |

Правила сопоставления: не больше трёх частей, без повторов; инициалы — по порядку (имя, затем отчество); человек берётся, только если подходит ровно один. Код сверяется с найденным человеком и с ролью поля (S — отправитель, R — получатель, C — курьер).

Что **не** делаем: не «исправляем» род фамилии (`Морозов Анна` — устойчивая особенность источника), не резолвим человека по одному коду, не принимаем одно имя без фамилии.

| Ситуация | Результат |
| :--- | :--- |
| пусто, `не указан` | `PERSON_EMPTY` — флаг, строка загружается |
| только код (`[S3]`, `[S3] не указан`) | `PERSON_CODE_ONLY` — карантин |
| латиница, цифры, посторонние символы | `PERSON_INVALID` — карантин |
| форма не распознана, человека нет в справочнике | `PERSON_UNKNOWN` — карантин |
| код не совпадает с ФИО / код чужой роли | `PERSON_CODE_CONFLICT` / `PERSON_ROLE_MISMATCH` — карантин |

### 3.5 Справочники из RAW

| Справочник | Как строится | Строк |
| :--- | :--- | ---: |
| `core.ref_city` | части «/ Город» отправителя и получателя; ключ без «г.», в нижнем регистре; написание — самое частое; встретившийся реже 3 раз — опечатка | 8 |
| `core.ref_person` | полные формы «Фамилия Имя Отчество» (≥ 3 раз); номер — код S/R/C##, стоящий рядом с этими фамилией и именем; город — самый частый | 20 |
| `core.ref_build_issue` | что не попало в справочники и почему (редкие формы, конфликты кодов) | 0 |

Справочник людей совпал с таблицей из профилирования (§11.3): 20 человек, у каждого один код, одно отчество и один город.

### 3.6 Числа и суммы

## 4. Этап 6. Карантин

### 4.1 Таблицы

| Таблица | Назначение |
| :--- | :--- |
| `core.stg_raw_row` | снимок RAW: `raw_row_id = md5(7 полей) : номер вхождения`, признак точного дубля |
| `core.stg_event_clean` | очищенные поля каждой строки, причины карантина `issues[]`, флаги качества `flags[]`, итог `outcome` |
| `core.quarantine` | очередь ручной обработки |
| `core.raw_row_outcome` | итог по каждой строке RAW: `LOAD` / `QUARANTINE` / `DUPLICATE` |
| `core.ref_quarantine_reason` | справочник причин: приоритет, описание, что делать вручную |
| `core.ref_setting` | отчётный период и шаг между этапами |

### 4.2 Итог строки

Приоритет: **DUPLICATE → QUARANTINE → LOAD**, одна строка — одна категория.

* **DUPLICATE** — точная копия другой строки (все 7 полей совпадают) или логический дубль (то же событие с теми же очищенными данными). У дубля хранится ссылка на оригинал.
* **QUARANTINE** — есть хотя бы одна причина.
* **LOAD** — строка корректна и загружается в core этапом 7.

### 4.3 Проверки уровня записи и посылки

Кроме ошибок разбора полей:

| Причина | Условие | Строк |
| :--- | :--- | ---: |
| `DT_OUT_OF_PERIOD` | дата вне отчётного периода (`ref_setting`) | 0 |
| `ROUTE_MISMATCH` | маршрут ≠ города отправителя и получателя | 0 |
| `SENDER_/RECEIVER_CITY_MISMATCH` | город в строке ≠ город человека | 0 |
| `SHIPMENT_PARTY_CONFLICT` | отправитель или получатель меняется внутри посылки | 0 |
| `SHIPMENT_COURIER_CONFLICT` | курьер меняется внутри посылки | 0 |
| `STATUS_MISLABELED` | «Доставлено» без всех 5 базовых этапов или раньше последнего из них | 58 |
| `STATUS_ORDER_CONFLICT` | базовый этап раньше по времени, чем предыдущий | 0 |
| `EVENT_KEY_CONFLICT` | одно событие (посылка, время, статус) с разными данными | 0 |

Проверки по времени учитывают только строки без проблем с датой, чтобы одна битая строка не утягивала в карантин всю посылку.

**Почему «Доставлено» в карантин, а не флаг** (отличие от §8 этапа 2). После снятия дублей у всех 2 000 посылок ровно 5 событий, и каждая строка «Доставлено» стоит на месте одного отсутствующего базового этапа, курьера в таких строках нет ни разу. Если загрузить их как доставку, в витринах «доставлено» окажется раньше «создано».

### 4.4 Карантин по главной причине

| Причина | Описание | Строк |
| :--- | :--- | ---: |
| `DT_PLACEHOLDER` | заглушка вместо даты (`NULL`, «неизвестно») | 352 |
| `DT_EMPTY` | дата не заполнена | 297 |
| `STATUS_PLACEHOLDER` | `???` вместо статуса | 171 |
| `DT_INVALID_TIME` | несуществующее время (`25:61`) | 136 |
| `DT_INVALID_DATE` | несуществующая дата (`31.02`) | 134 |
| `DT_RELATIVE` | «сегодня утром» | 130 |
| `STATUS_MISLABELED` | «Доставлено» вместо базового этапа | 53 |
| **Итого** | | **1 273** |

У записи может быть несколько причин (все хранятся в `reason_codes`); главная выбирается по приоритету. Всего `???` — 193 строки, «Доставлено» не на месте — 58: остальные попали в карантин по дате.

### 4.5 Что хранится в записи карантина

| Поле | Содержание |
| :--- | :--- |
| `raw_row_id` | ссылка на исходную строку |
| `source_table` | `public.raw_data_06` |
| `payload` | исходная запись целиком (`jsonb`, все 7 полей) |
| `primary_reason`, `reason_codes`, `reason_detail` | главная причина, все причины, понятное описание |
| `suggested_fix` | подсказка для ручной обработки |
| `is_active`, `deactivated_at` | в очереди ли запись сейчас |
| `first_detected_at` | когда запись впервые попала в карантин |
| `resolution_status`, `resolution_comment`, `resolved_at` | ручная обработка: `NEW` / `IN_PROGRESS` / `RESOLVED` / `REJECTED` |

**Подсказки.** События посылки идут с постоянным шагом 8 ч от первого этапа. По загружаемым строкам посылки вычисляется её начало `t0`, и для записи в карантине предлагается время (`t0 + 8 ч · (этап − 1)`), этап (по пропущенному месту) или оба. Подсказка есть у всех 1 273 записей; данные она не меняет — это помощь оператору, решение остаётся за человеком.

**Жизненный цикл.** Повторный запуск не трогает неизменившиеся записи и поля ручной обработки. Если у записи изменились причины или она вернулась в очередь, статус сбрасывается на `NEW`. Запись, которой больше нет в RAW, не удаляется, а помечается `is_active = false`.

### 4.6 Флаги качества (строка загружается)

| Флаг | Строк |
| :--- | ---: |
| `SAME_CITY_DELIVERY` — отправитель и получатель в одном городе | 1 147 |
| `RECEIVER_EMPTY` — получатель не указан в строке | 542 |
| `SENDER_EMPTY` — отправитель не указан в строке | 528 |
| `SELF_SHIPMENT` — отправитель = получатель | 372 |
| `COURIER_MISSING_ON_HANDOVER` — «Передано курьеру» без курьера | 110 |

Пустой участник в отдельной строке не мешает загрузке: внутри посылки участники не меняются, и у всех 2 000 посылок они находятся по другим строкам.

### 4.7 Контроль (`sql/05_checks.sql`)

Все проверки дают 0:

* неучтённые строки RAW (сверка по `raw_row_id`, а не по количеству);
* итоги строк, которых нет в RAW;
* баланс RAW = загружено + карантин + дубли;
* активный карантин совпадает со строками `QUARANTINE` в итогах;
* дубль ссылается на существующий оригинал, который сам не дубль;
* все причины есть в справочнике;
* у загружаемых строк заполнены обязательные поля;
* нет повторов ключа события среди загружаемых;
* у каждой записи карантина сохранена исходная строка.

## 6. Для этапа 7 (загрузка в core)

* Загружать строки `core.stg_event_clean` с `outcome = 'LOAD'`: в них уже разобраны посылка, время, статус, участники, города и маршрут.
* Участники посылки — из всех её `LOAD`-строк (внутри посылки они не меняются, конфликты уже отсеяны в карантин).
* Люди — `core.ref_person`, естественный ключ `(last_name, first_name, patronymic)`; `person_no` совпадает с кодом S/R/C##.
* Города — `core.ref_city`.
* Баланс для итоговой статистики — `core.v_raw_processing_summary`; после загрузки стоит сверить, что число событий в core равно числу `LOAD`.
